# V7.9 audit repair register

Date: 27 September 2026. Baseline: main `2d987c763929402cfa861eb4b73726dec9f32402` (V7.8). This register describes implemented repairs and their limits; it is not a certification that every production audit gate has closed.

The repair targets are the twenty JH findings from the 27 September health audit. The older F01–F22 production gates remain mandatory. CI installers are evaluation builds; automatic public release stays disabled. No claim of Siri-equivalent system integration, an actual human brain, zero future bugs, or a running commercial service is made.

## Repair status

“Fixed in code” means the identified behavior has a repair and focused regression coverage. Windows device observations and commercial provider acceptance are separate evidence. “Partial” identifies remaining engineering or physical validation, not a hidden pass.

## Verification

Before the repair, the local desktop suite had 426 tests and the service suite had 21. The repair adds focused fault/concurrency/security cases. The local final source run has 451 desktop tests (one Windows DPAPI test skipped on Linux) and 30 service tests. CI must run the exact submitted source on Python 3.11–3.14, the isolated service environments, and Windows 3.14 before promotion.

The Windows job builds and scans the frozen application and installer, checks secret exclusion, exercises desktop launch, installs/updates the app with data/settings sentinels, and injects a candidate version mismatch to test rollback. A successful hosted CI launch still does not test Adib's microphone, Bluetooth headset, speaker echo, sleep/resume or eight-hour background operation. Read the run linked from the PR for its actual result; this document alone does not turn a queued job into a pass.

Key new regression files: `tests/test_audit_repairs.py` and `tests_server/test_billing_recovery.py`. Existing expectations were updated where the previous tests encoded incorrect toggle, fake verification, premature wake or sandbox status behavior. No failing capability is enabled merely to make a status indicator green.

## Remaining launch gates

1. Run a physical Windows acceptance session on the supported device matrix: 100 wake trials per room/noise condition, inline command preservation, wrong-wake rejection, speech interruption, microphone permission denial, device unplug/replug, Bluetooth reconnect, sleep/resume, logoff/login and an eight-hour idle soak. Record p50/p95 acknowledgement and command latencies; agree on numeric acceptance targets before deciding pass/fail.
2. Deploy the API and billing worker behind HTTPS. Verify SMTP/reset delivery, Stripe test-mode checkout/portal/webhooks/renewal/failure/cancellation, commercial weather authentication and current account entitlements. Merchant secrets belong on the service host.
3. Complete semantic desktop/browser integration and reviewed generated-code isolation as separate engineering work with adversarial tests; do not change BLOCKED to PASS based on imports.
4. Apply main-branch protection with admin access, review licenses, produce signed build provenance/download locks and use an actual code-signing certificate. Validate signatures on a clean machine.
5. Fault-test update/restore and database restore with nonproduction data. Close each F01–F22 gate against the exact source commit and artifact checksum. Only then reconsider public-sale release publication.
