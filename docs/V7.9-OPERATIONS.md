# V7.9 operations and recovery

These are deployment/operator procedures, not evidence that a host or paid service already exists. Use a nonproduction account/database for the initial drill.

## Desktop setup

Create a local profile, then set the display name in Account / Subscription. In Background / Weather, select the city, enable wake listening and allow microphone access in Windows. “Wake up Jarvis” waits for the speech endpoint; a short acknowledgement comes before follow-up capture. Weather narration follows an empty command window, so an immediate command takes priority. The city is explicit; IP geolocation is not silently substituted.

Run the desktop once interactively before expecting remembered-login background startup. Keep the tray process running. Windows sleep suspends the application; it cannot listen while the OS is asleep. Test resume and device reconnect on the intended hardware. On a wedged native audio driver, wait for the reported recovery; if it cannot release the stream, reconnect the device or restart the app. Do not launch another hidden listener to force microphone ownership.

Local password recovery requires codes generated beforehand under Local profile with the current password. Save those codes offline. Generating a replacement set invalidates the previous set and remembered local sign-in; using one code resets the password and invalidates all remaining codes/sessions. The program does not ship a shared login or a password bypass.

For online service login, set the HTTPS origin under Online subscription. Register, request an email verification code, verify it, then use hosted Stripe checkout. Password reset uses a separate emailed code. Codes expire after 15 minutes. Optional “Remember online sign-in” works on Windows with DPAPI; the greeting can explicitly use the online name without changing local chat ownership. For existing plaintext API keys, use Connection settings → Save & Apply to write Windows-protected values. Keep historical backups private.

## Single-host backend deployment

1. Provision a supported Linux host, domain/TLS reverse proxy, dedicated `jarvis` system user and private `/var/lib/jarvis` directory. Place a reviewed checkout at `/opt/jarvis` owned by the deployment account; the service user must not edit its code.
2. Create `/opt/jarvis/.venv` and install `requirements-server.txt` with `constraints/linux.txt`. Run `pip check` and the service suite before switching the host.
3. Copy `deploy/service.env.example` to `/etc/jarvis/service.env` (root:jarvis, mode 0640). Supply the actual HTTPS origin, database path, Stripe test keys/prices/webhook secret, licensed commercial weather key and TLS SMTP settings. Do not commit this file or include it in a desktop build.
4. Install `deploy/jarvis-api.service` and `deploy/jarvis-billing-worker.service`, reload systemd, then enable/start both. The templates bind API traffic to loopback port 8000 and trust forwarded addresses only from the loopback reverse proxy. Restrict direct access and configure the proxy's body/time limits and logs without credentials or request bodies.
5. Register the signed Stripe endpoint `/billing/webhook`, configure the customer portal, and complete test-mode lifecycle checks. The worker retries the durable billing inbox every 30 seconds with backoff; events reaching 20 attempts need operator attention. `/health` exposes configuration/backlog indicators, not secret values or proof of provider reachability.
6. Deliver reset/verification mail to real test inboxes. Configure provider rate/reputation controls. A restarted API may drop an in-flight background email; resend through the same rate-limited endpoint. This version has no durable mail queue.

Use one service host with the shared local SQLite database. Multiple local API processes share database leases/rate counters; this is not a multi-region database design. Monitor disk space, database errors, failed/dead-letter billing events, SMTP failures, authentication abuse and provider request latency. Set up host-level monitoring/alerts; none are provisioned by the repository.

## Backups and restore

Take an online snapshot with an exclusive new filename:

```bash
/opt/jarvis/.venv/bin/python -m server.backup \
  --database /var/lib/jarvis/accounts.sqlite3 \
  --output /var/backups/jarvis/accounts-YYYYMMDD-HHMMSS.sqlite3
```

The command uses SQLite's backup API, checks integrity, limits snapshot time and never overwrites an existing backup. It does not encrypt off-host storage or schedule retention. Use restricted encrypted storage, a retention policy and an independently tested off-host copy.

For a restore drill, stop both API and worker, preserve the current database **and its WAL/SHM sidecars together** in a separate recovery directory, restore the selected snapshot into a fresh path with the service user's permissions, and run `PRAGMA integrity_check`. Point `JARVIS_SERVER_DB` at that fresh path; never attach old WAL files to the restored snapshot. Start the services and verify test login, account count and entitlement reconciliation with the provider. A restored historical database may not know later payment actions; inspect provider state before allowing checkout. Never erase an uncertain intent just to make a retry succeed.

## Billing reconciliation

An uncertain checkout is retried using its durable provider idempotency key. After 23 hours, the program blocks replay because the provider may retire the old key. Inspect the customer, Checkout Session and subscription in the merchant test dashboard. Record the observed provider identifiers and decide an explicit repair under maintenance; there is intentionally no automatic delete-and-create fallback. Do not edit live billing rows while a lease owner is active.

For a failed webhook, inspect event ID, attempt count, retry time and safe error class in `billing_inbox`; never log full webhook bodies or keys. Fix connectivity/configuration and retry under an operator-reviewed procedure. A success redirect alone never grants Pro. Past-due/canceled/stale or unverified entitlements fail closed.

## Uncertain desktop actions

The durable effect ledger records intent before a side effect. A crash or ambiguous failure may leave `INTENT`/`UNCERTAIN`, blocking an identical retry. Inspect the actual destination/application first. In a checkout running under the affected profile environment:

```bash
python -m jarvis.recover_action
python -m jarvis.recover_action INTENT_ID --observed observed_applied
# Or, only after observing it did not happen:
python -m jarvis.recover_action INTENT_ID --observed observed_not_applied
```

Resolution is audited and does not itself replay the action. A live process's in-flight intent cannot be resolved out from under it. These controls prevent blind duplication; they do not promise exactly-once external execution.

## Windows update recovery

The V7.9 updater retains `<AppDir>.rollback` containing only its executable, `_internal` libraries, update helper, manifest and journal. User `data/` and `.env` are not restored/deleted. It checks the downloaded installer hash twice, waits for the old process, validates every checkpoint file/hash, then runs the candidate import/Tk/schema/version probe. After a completed failed install, it restores the verified binary checkpoint and asks for a manual restart. No crash loop automatically retries the update.

If `checkpoint.json` says `prepared`/`installing`, preserve the checkpoint and installer logs. Confirm all installer/JARVIS processes have exited before any manual restore. Back up current user state separately. Verify `files.json` against the checkpoint, restore only the three owned binary paths, verify again, and test launch. Installer/uninstaller registry metadata may still need repair with the prior signed installer. Do not copy an older user database over newer data as a shortcut. Disk-full/power-loss recovery and all supported prior-version upgrades still need a physical drill. Older installed update helpers do not retroactively gain V7.9 rollback protection.

## Release controls

`.github/branch-protection.main.json` is the proposed GitHub admin policy; its presence does not apply it. Apply with repository administration access and verify the required checks/review settings. `scripts/sign_windows_release.ps1` signs a supplied file using a real private-key certificate already in the Windows certificate store and verifies the result; it is not automatically wired into CI and does not invent a certificate. Sign the application before packaging and sign the final installer, then scan and rerun package/installer tests on those exact signed artifacts.

Dependency inventories capture package metadata and installed RECORD hashes. They are useful audit inputs, not independent file rehash attestations, complete license approval or reproducible hash-locked downloads. The vulnerability job must fail on known vulnerabilities or an unavailable audit feed. Public release publication remains disabled pending the repair register and F01–F22 closure evidence.
